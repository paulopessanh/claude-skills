# The manual as a living document

Confidence key: 🟢 published primary source · 🟡 secondary or judgment · 🔴 folklore.

## One source, several views

Three documents carry the same numbers: the reveal deck, the team guidelines and the manual. If each is edited by hand, they
drift. The rule: the technical numbers have **one source** (the approved guidelines spec). Everything else quotes it. If two
documents disagree, the latest approved one wins and the other is corrected, and the correction is recorded.

## Born early, grown at each approval

Start the manual at step 1. At each approved step, add its section. At the end nothing is rebuilt from memory, and the manual
is also the proof of the process that built the brand.

## Two versions

- **Internal (source):** everything. Decisions with date and author, client changes with the opinion, discarded alternatives,
  registries, links to documents and decks.
- **Client (published):** what the client needs to apply the brand: searchable, colour codes that copy in one click, downloadable
  signatures, elements and tokens, readable on a phone, light and dark. Always at the same address, with a visible version.

The client version is generated from the internal one. Never edit one without reflecting it in the other.

## Versions and the change history

Number versions so a reader can tell the size of a change: a patch for a correction, a minor for an addition, a major for
a change that breaks something already applied (a new mark, a changed colour). Keep a dated history: what changed, why, who approved.
Superseded finals move to `Old`; only approved files sit in the delivery folder.

## When a change arrives

A change to the mark, a colour, a typeface or an element: update the team guidelines first, then the manual, then check each
derived element and every piece that used it. The step graph in `brand_state.py` marks the downstream steps stale so nobody forgets.

## Sources

1. 🟢 Tom Preston-Werner, *Semantic Versioning 2.0.0*, semver.org. Version numbers that communicate the size of a change.
2. 🟢 Olivier Lacan, *Keep a Changelog* 1.1.0, keepachangelog.com. A human-readable dated change history.
3. 🟢 David Parnas, "On the Criteria To Be Used in Decomposing Systems into Modules", *Communications of the ACM* 15(12), 1972. Hide a decision in one place so a change touches one place.
4. 🟢 Andrew Hunt and David Thomas, *The Pragmatic Programmer*, Addison-Wesley, 1999. "Don't repeat yourself": every piece of knowledge has one authoritative representation.
5. 🟡 Daniele Procida, *Diátaxis*, diataxis.fr. Separating tutorials, how-to guides, reference and explanation helps documentation stay usable.
6. 🟢 Alina Wheeler, *Designing Brand Identity*, 5th ed., 2017. Managing assets as the last phase of the process.

## Claims to hold loosely

- 🔴 "A brand manual is a PDF you finish." A manual that is not maintained is wrong within months.
- 🟡 Semantic versioning was made for software. Applied to a brand, the idea (the number tells the size of the change) travels; the exact rules need a local definition.
